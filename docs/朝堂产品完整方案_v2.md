# 朝堂 — 多角色辩论式 AI 对话工具 完整方案（v2）

> **更新说明**：基于原方案新增 **Skill 系统** 和 **Function Call 系统** 详细设计，并补充最小 Agent 所需基础能力清单。

---

## 一、产品定位

**朝堂**是一个多角色辩论式 AI 对话工具。用户扮演皇上，提出议题后，多个朝臣角色依次进言，用户可拍板定夺或点名追问。每个角色可独立配置 LLM，利用不同模型的风格差异获得更丰富的意见。产品同时支持"朝议模式"和"模型对比模式"，满足两种使用场景：

- **朝议模式**：6 个角色串行发言，后发言者能看到前文，有交锋感和戏剧感。
- **模型对比模式**：同一问题发给多个模型，结果并排展示，方便横向评测。

Slogan：**百官进言，圣裁由你。**

---

## 二、核心流程

### 2.1 朝议模式流程

用户输入议题 → 按顺序串行调用各角色 LLM（后发言者可见前文） → 各角色依次进言，流式渲染 → 用户选择：拍板 / 点名追问 / 开启新议题 → 拍板后生成"圣旨"存档

### 2.2 模型对比模式流程

用户输入议题 → 同一问题发给多个模型 → 结果并排展示 → 支持三种节奏：串行 / 并行 / 盲审

### 2.3 三种节奏

| 节奏 | 说明 | 适用场景 |
|------|------|----------|
| **串行** | 模型依次输出，后一个能看到前一个的回答 | 深度讨论、需要交锋感 |
| **并行** | 多个模型同时输出，互不可见 | 快速对比、效率优先 |
| **盲审** | 并行输出但隐藏模型名称，揭晓前不知道谁说的 | 公平评测、消除偏见 |

## 三、角色设计

### 3.1 六大臣

| 角色 | 官职 | 定位 | 风格 |
|------|------|------|------|
| 丞相 | 百官之首 | 全局视角，综合判断 | 稳重、全面、善于总结 |
| 户部尚书 | 财政大臣 | 经济、成本、收益分析 | 精明、数据驱动 |
| 御史 | 监察官 | 挑刺、质疑、风险警示 | 犀利、批判性强 |
| 大将军 | 军事统帅 | 竞争、战略、执行力 | 果断、行动导向 |
| 太傅 | 帝师 | 历史、文化、长远视角 | 博学、引经据典 |
| 总管 | 内务总管 | 舆情、民心、可操作性 | 接地气、察言观色 |

### 3.2 备选角色组（可扩展）

- **文官组**：丞相 + 户部尚书 + 太傅（偏理性分析）
- **武官组**：大将军 + 御史 + 总管（偏行动和风险）
- **混合组**：默认六人（均衡）

### 3.3 System Prompt 设计

每个角色有独立的 System Prompt，定义其：
- 身份和官职
- 说话风格（文言文程度、用词习惯）
- 分析问题的角度和偏好
- 与其他角色的互动方式（如御史喜欢反驳丞相）

## 七、Agent 化路线图

> 朝堂的定位是工具，不是游戏。Agent 化是为了让每个大臣从"会说话"变成"会做事"，让产品从"模型对比展示台"升级为"能主动执行任务的多 Agent 协作系统"。

### 7.1 为什么分两步走

**第一步：完成方案中的核心功能**

把现有的设计落地——多角色辩论 UI、三种对比节奏（串行/并行/盲审）、Markdown 导出存档。这一步做完，你已经有一个能用的产品了，用户价值是完整的。

**第二步：在此基础上做 Agent 化改造**

这时候底层已经有了稳定的数据模型和 UI 层，Agent 化更像是"给每个大臣装上工具"：
- 丞相变成 coordinator，负责任务拆解和汇总
- 其他大臣变成 worker agent，各自带工具（搜索、数据、事实核查等）
- 朝议变成任务编排，拍板后 agent 继续执行后续动作

### 7.2 这样做的好处

1. **MVP 可交付**：第一步做完就能用，不用等 agent 架构全部搭好
2. **架构兼容**：第一步设计的数据模型（Minister / Speech / DebateRound）天然适合 agent 化，不需要推倒重来
3. **风险可控**：agent 框架（LangGraph / CrewAI）的选型和调试可以慢慢来，不影响前端体验
4. **用户反馈循环**：先上线让用户体验，拿到反馈再决定 agent 化优先做哪个角色

### 7.3 Agent 化核心转变

| 现在 | Agent 化之后 |
|------|-------------|
| 用户问，模型答 | 用户给目标，agent 自己拆解、执行、汇报 |
| 6 个角色各说各的 | 角色之间有分工、有协作、有反馈循环 |
| 输出是文本 | 输出是行动结果（搜了资料、写了报告、做了决策建议） |

### 7.4 给每个角色配工具

- **丞相**：能调用搜索工具，查政策背景、历史案例
- **户部尚书**：能调数据工具，算账、拉图表、做预算表
- **御史**：能调事实核查工具，交叉验证前面说法的真伪
- **大将军**：能调地图/情报工具，分析地理和局势
- **太傅**：能调知识库，引经据典、查历史先例
- **总管**：能调舆情工具，看社交媒体/新闻风向

每个 agent 不是"凭感觉说"，而是"先查再判断"。

### 7.5 朝议变成任务编排

用户给一个目标，比如"帮我分析一下要不要投资某行业"：

```
丞相（协调者）：拆解问题 → 分配子任务给各 agent
户部尚书：去查财务数据、市场规模
御史：去查风险、负面新闻、监管动态
大将军：去查竞争格局、进入壁垒
太傅：去查行业历史、周期规律
总管：去查舆情、政策风向
丞相汇总：综合各方信息，给出建议
用户拍板
```

这就是一个完整的 **multi-agent workflow**。

### 7.6 退朝后办事

朝议结束不是终点。用户拍板后，agent 可以继续执行：
- 生成完整报告（Markdown）
- 自动发邮件/消息给相关人员
- 创建待办事项
- 持续监控某个指标，有变化再上奏

### 7.7 架构变化

```
现在：用户 → 模型 → 输出

Agent 化：用户 → 协调者 agent → 分配任务 → 多个 worker agent（各带工具）→ 汇总 → 输出 → 执行后续动作
```

朝堂只是 UI 包装，底层是一个标准的 multi-agent 框架。可以用现有的 agent 框架（比如 LangGraph、CrewAI）来搭，每个大臣就是一个 agent node。

### 7.8 丞相变成 Coordinator Agent

丞相要变成 coordinator agent，它不只是"第一个发言的角色"，而是真正负责任务拆解和结果汇总的那个。其他大臣是 worker agents，各司其职。

这样产品就从"好看的模型对比工具"升级成"有分工、有工具、能执行的多 agent 系统"，朝堂只是它的外壳。

## 八、🆕 Skill 系统设计

> Skill 是可插拔的能力模块，定义了角色"会什么"。与 Function Call（底层工具调用机制）不同，Skill 是更高层的能力抽象，一个 Skill 可以组合多个 Function Call。

### 8.1 Skill 与 Function Call 的关系

```
┌─────────────────────────────────────────┐
│  Skill（能力层）                          │
│  "搜索政策背景" "分析财务数据" "事实核查"   │
├─────────────────────────────────────────┤
│  Function Call（工具调用层）               │
│  web_search() calculate() fact_check()  │
├─────────────────────────────────────────┤
│  LLM Provider（模型层）                   │
│  OpenAI / Claude / Ollama / DeepSeek    │
└─────────────────────────────────────────┘
```

- **Function Call**：LLM 原生的工具调用能力，通过 JSON Schema 定义工具，LLM 决定何时调用
- **Skill**：面向角色的能力封装，一个 Skill = 一组相关的 Function Call + 使用策略 + 结果处理逻辑

### 8.2 Skill 定义接口

```typescript
/**
 * Skill 定义 - 角色的一项能力
 */
export interface Skill {
  id: string;                    // 唯一标识，如 'web_search'
  name: string;                  // 显示名称，如 '网络搜索'
  description: string;           // 能力描述，供 LLM 理解何时使用
  icon?: string;                 // 图标
  category: SkillCategory;       // 分类
  tools: ToolDefinition[];       // 该 Skill 包含的 Function Call 工具列表
  config?: SkillConfig;          // 可选配置
  enabled: boolean;              // 是否启用
}

export type SkillCategory = 
  | 'information'    // 信息获取类（搜索、查询）
  | 'analysis'       // 分析计算类（数据分析、图表）
  | 'verification'   // 验证核查类（事实核查、交叉验证）
  | 'generation'     // 内容生成类（报告、公文）
  | 'communication'  // 通信类（邮件、消息）
  | 'system';        // 系统类（文件操作、日程管理）

export interface SkillConfig {
  maxCallsPerRound?: number;     // 每轮朝议最多调用次数
  timeout?: number;              // 超时时间（ms）
  requireConfirmation?: boolean; // 是否需要用户确认才执行
  cacheResults?: boolean;        // 是否缓存结果
}
```

## 九、🆕 Function Call 系统设计

> Function Call 是 LLM 原生的工具调用机制。通过 JSON Schema 向 LLM 描述可用工具，LLM 在需要时自主决定是否调用、传什么参数。

### 9.1 工具定义格式（OpenAI-compatible）

```typescript
/**
 * Function Call 工具定义 - 遵循 OpenAI tools schema
 */
export interface ToolDefinition {
  type: 'function';
  function: {
    name: string;              // 函数名，如 'web_search'
    description: string;       // 函数描述，LLM 据此判断何时调用
    parameters: JSONSchema;    // 参数定义（JSON Schema）
  };
}

/**
 * LLM 返回的工具调用请求
 */
export interface ToolCall {
  id: string;                  // 调用 ID
  type: 'function';
  function: {
    name: string;
    arguments: string;         // JSON 字符串
  };
}

/**
 * 工具执行结果
 */
export interface ToolCallResult {
  toolCallId: string;         // 对应的调用 ID
  functionName: string;
  arguments: Record<string, any>;
  result: any;                 // 执行结果
  status: 'success' | 'error' | 'timeout';
  duration: number;            // 执行耗时（ms）
}
```

### 9.2 Function Call 调用流程

```
┌──────────┐     ┌──────────┐     ┌───────────┐     ┌──────────┐
│  用户输入  │ ──→ │  LLM 推理 │ ──→ │ 工具调用？  │ ──→ │ 执行工具  │
└──────────┘     └──────────┘     └───────────┘     └──────────┘
                                       │ 否              │
                                       ↓                 ↓
                                  ┌──────────┐     ┌──────────┐
                                  │ 直接回复  │     │ 结果回传  │
                                  └──────────┘     │ 给 LLM   │
                                                   └──────────┘
                                                         │
                                                         ↓
                                                   ┌──────────┐
                                                   │ LLM 综合  │
                                                   │ 结果回复   │
                                                   └──────────┘
```

**详细步骤**：

1. **构建请求**：将用户消息 + 角色 System Prompt + 可用 tools 定义一起发给 LLM
2. **LLM 决策**：LLM 返回普通文本（不需要工具）或 `tool_calls`（需要调用工具）
3. **执行工具**：前端/主进程收到 `tool_calls` 后，执行对应的工具函数
4. **结果回传**：将工具执行结果作为 `tool` role 的 message 回传给 LLM
5. **最终回复**：LLM 综合工具结果，生成最终回复（可能再次调用工具，形成循环）
6. **记录存档**：将工具调用过程记录到 Speech.toolCalls 中

### 9.4 工具执行器（ToolExecutor）

```typescript
/**
 * ToolExecutor - 在 Electron 主进程中执行工具调用
 */
export class ToolExecutor {
  private handlers: Map<string, ToolHandler> = new Map();
  
  // 注册工具处理器
  registerHandler(name: string, handler: ToolHandler): void;
  
  // 执行工具调用
  async execute(toolCall: ToolCall): Promise<ToolCallResult>;
  
  // 批量执行（并行模式下的多个工具调用）
  async executeBatch(toolCalls: ToolCall[]): Promise<ToolCallResult[]>;
}

export type ToolHandler = (args: Record<string, any>) => Promise<any>;
```

### 9.5 安全沙箱

工具执行必须在安全沙箱中运行：
- **网络请求**：通过 Electron 主进程代理，前端不直接访问外部 API
- **文件系统**：限定可访问目录，禁止任意读写
- **超时控制**：每个工具调用有最大超时时间
- **用户确认**：高危操作（如发邮件、删除文件）需用户确认

## 十、🆕 最小 Agent 基础能力清单

> 要实现最基本的 Agent 功能，以下是按优先级排列的基础 Function Call 和 Skill 清单。

### 10.1 通用基础工具（所有角色可用）

| 优先级 | 工具名 | Function Call | 说明 | 复杂度 |
|--------|--------|---------------|------|--------|
| P0 | 网络搜索 | `web_search(query, max_results?)` | 搜索引擎查询，返回摘要结果 | 低 |
| P0 | 知识问答 | `knowledge_query(question, context?)` | 基于本地知识库的 RAG 检索 | 中 |
| P1 | 计算器 | `calculate(expression)` | 数学表达式求值 | 低 |
| P1 | 文件读取 | `read_file(path)` | 读取本地文件内容 | 低 |
| P1 | 文件写入 | `write_file(path, content)` | 写入文件到本地 | 低 |
| P2 | 日期时间 | `get_datetime()` | 获取当前日期时间 | 极低 |
| P2 | 待办创建 | `create_todo(title, description?, due_date?)` | 创建待办事项 | 低 |

### 10.2 角色专属工具

#### 丞相（Coordinator）

| 工具名 | Function Call | 说明 |
|--------|---------------|------|
| 任务拆解 | `decompose_task(goal, sub_agents[])` | 将目标拆解为子任务并分配 |
| 结果汇总 | `summarize_results(results[])` | 综合多个 worker 的结果 |
| 追问调度 | `request_clarification(minister_id, question)` | 要求某个角色补充信息 |

#### 户部尚书

### 10.3 最小可行 Agent 的 5 个必备工具

如果只能实现最少的工具来让 Agent "能跑起来"，优先级如下：

| # | 工具 | 理由 |
|---|------|------|
| 1 | **web_search** | Agent 最核心的能力——获取外部信息，不再"凭感觉说" |
| 2 | **knowledge_query** | 本地 RAG，让角色能引用领域知识 |
| 3 | **calculate** | 数值推理，让户部尚书等角色能做定量分析 |
| 4 | **read_file** | 读取本地文件/文档，扩展信息来源 |
| 5 | **summarize_results** | 丞相必备，能汇总多个 worker 的结果 |

有了这 5 个工具，就已经能实现一个基本的 **"用户给目标 → 丞相拆解 → 各角色查资料 → 丞相汇总 → 给出建议"** 的 multi-agent workflow。

## 十三、安全建议

API Key 不要直接放在 Vue 渲染进程里。

Electron 下建议这样走：

```
Vue 渲染进程 → ipcRenderer → Electron 主进程 → OpenAI / Ollama API
```

Tauri 下则通过 Rust command 调用，避免 Key 泄露。

Function Call 工具执行必须在主进程沙箱中，前端不直接执行工具逻辑。

## 十四、总结

**朝堂**产品的核心设计理念是：通过角色人设 + LLM 风格差异 + 朝堂仪式感 UI，打造一个既有实用价值又有情感体验的 AI 对话工具。

产品提供两种核心模式：
- **朝议模式**：6 个角色串行发言，后发言者能看到前文，有交锋感和戏剧感。
- **模型对比模式**：同一问题以串行/并行/盲审三种节奏发给多个模型，结果并排展示，方便横向评测。

**v2 新增**：通过 **Skill 系统** 和 **Function Call 系统**，每个角色从"会说话"升级为"会做事"。Skill 是可插拔的能力模块，Function Call 是底层工具调用通道。二者结合，使朝堂从"模型对比展示台"进化为"多 Agent 协作系统"。

**发展路径**：先完成核心功能（Phase 1-2），让产品可交付可用；在此基础上搭建 Skill + Function Call 基础设施并做 Agent 化改造（Phase 3），让大臣从"会说话"变成"会做事"；最后扩展高级功能（Phase 4），如圣旨/诏书生成器、史官实录等工具增强功能。整个过程中保持工具属性，不做游戏化数值设计。
