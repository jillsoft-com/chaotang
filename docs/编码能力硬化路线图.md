# 编码能力硬化路线图

> 状态：设计方案，尚未实施。目标产品是 Electron 桌面版编程 Agent；不建设内嵌 IDE。本文中的文件名与接口是实施建议，开发时以现有类型和安全边界为准。

## 一、目标与现状

用户选择工作目录并给出任务后，朝堂应能定位代码、精确修改、运行必要检查、针对失败修复，并交付可审阅的差异与证据。**节点完成必须代表程序核验通过；模型声称完成不能代替验收。**

当前已有 `read_file`、`write_file`、`search_code`、`run_tests`、命令执行、工具级 diff、任务树及中断快照。主要缺口如下：

| 现状 | 对编码任务的影响 |
| --- | --- |
| `write_file` 对现有文件整文件覆盖；`refactor_rename` 使用文本搜索与正则替换 | 易覆盖并发修改，跨文件改名可能误改或漏改 |
| 自主引擎有“构建失败后修复”的提示词；节点 `acceptance` 字段尚未成为完成门槛 | 模型可未运行检查便结束，或把失败任务报成完成 |
| `repository-context.ts` 已有目录扫描与 TF-IDF 关键词索引，普通大臣流程会注入；任务树 Worker 未复用此入口 | Agent 模式缺少自动仓库上下文 |
| 有工具级 diff 和任务树快照 | 缺少一次任务的完整变更审阅、验收记录与恢复时文件冲突核对 |

本路线图以**正确交付优先于自动继续**为原则。无法证明文件版本、测试结果或恢复状态时，任务应暂停并说明原因。所有新工具沿用现有工作目录授权、危险命令审批、只读任务隔离和预算限制。

## 二、实施顺序与发布门槛

| 阶段 | 交付物 | 发布门槛 |
| --- | --- | --- |
| P0-A 精确编辑 | `search_replace` 与版本校验、单文件安全写入 | 旧内容不匹配、版本冲突、审批拒绝时原文件不变；差异可查看 |
| P0-B 编码验收 | 一个统一的验收状态机，覆盖任务树、自主和普通 Worker 编码路径 | 必需检查未通过或未执行时不得标记完成；失败证据可回查 |
| P0-C 修复循环 | 基于真实诊断的有限修复与重新验收 | 达到预算或次数上限后停止，保留未完成状态和诊断 |
| P1-A 仓库上下文 | 复用现有索引并接入任务树 Worker，写后失效 | Worker 能找到相关文件；修改后不会继续引用旧内容 |
| P1-B 桌面审阅 | 一次任务的文件清单、完整 diff、检查结果与未完成事项 | 用户能区分已验证、未验证、失败，不依赖模型叙述 |
| P1-C 恢复与撤销 | 文件版本核对、待验收重跑、受约束的撤销 | 重启与外部修改不会静默覆盖用户文件 |

P0-A 与 P0-B 可分别开发，但两者接线后才能宣布“编码任务硬化完成”。多文件编辑与符号检索在基础路径稳定后再扩展；向量索引不列为一期前置条件。

## 三、P0-A：精确编辑与文件保护

### 3.1 工具契约

新增 `search_replace` 工具及 Electron `patch-file` IPC。修改现有文件时优先使用；`write_file` 保留给新文件和用户明确要求的整文件生成。工具参数至少包含：

```typescript
interface PatchFileInput {
  path: string                  // 工作目录内路径，主进程重新解析授权
  expectedSha256: string        // 修改现有文件必填；来自最近一次读取
  patches: Array<{
    oldText: string             // 非空；默认必须唯一命中
    newText: string
    replaceAll?: boolean        // 显式开启，且返回实际命中数量
  }>
}
```

`read_file` 应返回文件内容及 SHA-256；不能让模型自行计算或编造 `expectedSha256`。主进程在写入前重新读取并校验哈希。一次调用中的多个 patch 按顺序作用于内存中的虚拟内容；任一 patch 未命中、非唯一命中或版本不符，整次调用不写盘。返回稳定错误码、当前哈希、命中数及写后哈希，供模型决定重新读取或暂停。

### 3.2 桌面主进程的写入边界

- 复用 `resolveAuthorizedPath`、文件类型与大小限制、覆盖审批；拒绝目录、二进制文件、越界路径以及经符号链接逃逸的目标。
- 对同一文件的并发写入加锁；在真正替换前再次校验版本。保留原有换行符、BOM 与合理的文件权限。
- 同目录写临时文件，再采用经过 Windows 实测的安全替换流程；写入或替换失败时保留原文件并清理临时文件。不要把“先校验后调用 `writeFileSync`”写成磁盘原子性保证。
- 记录本次操作的前后哈希、路径与 diff。日志仅保存必要元数据；不把整个仓库文件内容塞进会话快照。

### 3.3 全链路接入

同步修改 `electron/preload.cjs`、`src/env.d.ts`、工具定义与注册、普通会话和 `coordinator.ts` 的路径注入、自主引擎、动态工具选择、`WRITE_TOOLS` 与只读过滤、资源锁、工具状态及 diff 捕获。只读节点即使模型伪造工具调用，也必须在主进程写入前被拒绝；若由 IPC 执行此校验，须使用主进程可信的任务权限上下文或一次性能力凭证，不能相信渲染进程传来的 `readOnly: false`。

`refactor_rename` 在未实现语法级引用分析前，保持“预览并逐项确认”的定位；不得宣传为安全的语义重构。文本替换不能跨越源码、字符串和注释的语义边界。

### 3.4 多文件改动

单文件补丁成功后再设计 `batch_patch`。跨多个文件的“全部预校验、逐个写入”**不具备文件系统级原子性**；文档与界面不得承诺绝对原子。

可采用预校验、备份或操作日志、逐文件提交、失败时有条件回滚的方案。回滚前必须比较目标文件与本次写后哈希；若文件已被外部修改，应停止自动回滚并报告冲突，绝不覆盖新内容。进程崩溃后可依据日志识别“部分提交”，交由恢复流程处理。

## 四、P0-B：强制编码验收

### 4.1 先确定任务与基线

将“会修改工作目录的任务”标为编码任务，不仅依赖 `node.mode === 'action'`，也要覆盖普通会话、自主引擎和旧版扁平 Worker 路径。开始前记录 Git 状态或文件基线，区分用户原有改动与本次改动。不能只从 `write_file` 的工具参数收集路径：命令、Git 操作及其他工具也可能改文件。

编码任务的验收计划应在执行前形成，包含用户明确标准、项目可用的检查命令和适用范围。命令从项目实际脚本或用户指定项选取；项目没有测试脚本时标为“未配置”，不能默默视为通过。运行命令仍走现有授权与沙箱流程，不通过验收器绕过审批。

### 4.2 单一验收状态机

在 `src/services/agent/acceptance-gate.ts` 建立统一接口，由各执行路径调用同一套规则：

```typescript
type GateState = 'pending' | 'running' | 'passed' | 'failed' | 'unverified'

interface CheckRecord {
  kind: 'test' | 'typecheck' | 'build' | 'user_requirement'
  command?: string
  cwd?: string
  exitCode?: number
  timedOut?: boolean
  status: GateState
  outputRef?: string             // 完整输出的存储引用
  summary: string                // 给模型与用户看的有界摘要
  startedAt?: number
  finishedAt?: number
}
```

验收器先确认本次改动清单与预定检查，再执行检查并记录真实退出码、超时和诊断。输出可截断展示，完整诊断保留引用。`goalReached`、模型总结、一次成功的写工具调用，都不能直接把编码节点标为 `completed`。有必需检查失败、超时、拒绝授权或未运行时，节点保持未完成状态，并说明是 `failed`、`paused` 还是 `unverified`；不得伪造“通过”。

将结果落到任务节点和持久化快照，父节点与最终汇报直接读取程序记录。不要在调度器和自主引擎各跑一套验收，避免重复命令、结果不一致及预算重复扣费。调度器负责状态收束；执行器调用同一个验收服务并返回结果。

### 4.3 有界修复循环

检查失败时，将失败命令、退出码、关键诊断与本次差异交给原执行者修复；修复后必须重新运行受影响检查。默认设置有限的修复次数，并同时受节点 token、工具调用和时间预算约束。每次修复前重新读取当前文件版本；同一失败无新证据时避免空转。预算或重试上限耗尽则停止，保留差异和失败证据供用户审阅。

对修改了源码而无可用自动检查的任务，默认给出 `unverified`，由用户明确验收后才能视为交付完成。文档类修改可配置较轻的检查策略，但同样需要记录实际检查了什么。

## 五、P1-A：让任务树 Worker 使用现有仓库索引

复用 `repository-context.ts` 中的 `getProjectIndex`、`searchProjectIndex` 和 `generateContextHint`，不要再造第二个十分钟缓存。任务树启动时获取项目索引；每个 Worker 按自己的任务检索相关文件，将短摘要和文件行号注入其上下文，并允许继续调用 `search_code`、`read_file` 深查。普通会话和任务树共用同一套索引策略。

成功写入、创建、删除或重命名文件后，使相应项目缓存失效；先用可靠的按项目重建，之后再考虑增量更新。十分钟 TTL 只能兜底，不能替代写后失效。外部编辑则在使用前核对修改时间或提供手动刷新。

当前索引是关键词检索，最多处理部分文件；应在界面和日志中标示索引文件数、跳过数量和构建时间。下一步可做符号定义/引用检索；需要跨语言可靠重构时再引入解析器。向量检索须以真实任务评估收益后决定。

## 六、P1-B：桌面交付审阅

在现有 `ChatSession.vue` 中增加一次任务的交付面板即可，不建设 IDE。面板展示：

1. 本次任务修改的文件及新增、删除、修改状态；与任务前基线比较的完整 Git diff 或等效差异。现有工具卡片的 100 行预览仍可保留，但不能充当完整交付记录。
2. 每条必需检查的命令、退出码、耗时、完整输出入口与 `passed/failed/unverified` 状态。
3. 已完成要求、失败节点、未解决事项、人工批准记录；程序生成的状态与模型解释分开呈现。
4. “确认交付”只记录用户已审阅，不改写测试结果。“撤销本次改动”只在本次操作有可恢复基线且当前文件仍等于本次写后版本时提供；冲突时让用户自行处理。

会话中可继续保留流式文本和工具状态；交付面板负责最终核验，不要求内嵌编辑器、终端或复杂代码导航。

## 七、P1-C：重启恢复与文件冲突

现有任务树快照可恢复节点调度。新增的恢复元数据至少包括：节点 ID、验收计划与状态、已执行检查记录、本次变更文件的写前/写后哈希、未完成的文件操作日志。大型 diff 和命令输出存独立文件或数据表，快照仅保存引用，避免历史会话膨胀。

重启时先读取磁盘真实状态：

- 当前哈希等于本次写后哈希：可继续尚未执行的验收；已执行但无法证明有效的检查需重跑。
- 当前哈希等于写前哈希：视为写入未落盘或已被撤销，不可直接跳过编辑步骤。
- 两者均不等：暂停并展示冲突。默认保留当前文件；只有明确存在备份、且用户确认时才提供恢复旧内容。

恢复前重查 Git 状态与工作目录授权。不得把“以当前文件为准继续”解释为自动采纳文件已满足原验收标准；仍需重新检查。需用真实桌面进程终止与重启验证，而不只测快照序列化。

## 八、验收样本与质量门禁

建立独立样本仓库，至少覆盖下列场景；每轮从干净基线重新生成样本，并保存实际 diff、检查输出和任务事件：

| 场景 | 必须观察的结果 |
| --- | --- |
| 单文件缺陷修复、跨文件接口调整 | 改动限于目标文件；相关测试与构建实际通过 |
| 原文件被外部编辑、片段出现两次 | 补丁拒绝写入，用户的新内容不丢失 |
| 第二个补丁失败、第三个文件提交失败 | 单文件不部分写入；跨文件留下明确的恢复记录，不声称原子成功 |
| 测试失败、超时、无测试脚本、用户拒绝命令 | 不标记完成；失败原因和未验证项可见 |
| 连续修复无进展、预算耗尽 | 有界停止，不持续烧模型或覆盖文件 |
| 执行中杀进程、重启后外部修改 | 文件冲突被识别；不自动覆盖；验收按需重跑 |
| 同一任务在普通会话、任务树、非自主 Worker 路径执行 | 使用同一验收规则，不出现路径间“完成”口径差异 |

测试分层：纯逻辑单测验证匹配与状态推导；Electron IPC 集成测试验证授权、真实文件写入和冲突；桌面端到端测试验证审阅及恢复；使用真实模型的受控任务验证规划、修复与最终产物。现有 249 项单测和构建通过只能说明已有覆盖路径无回归，不能替代新增路径验收。

记录可比较的指标：任务实际完成率、错误完成率、误覆盖/漏改次数、首次通过率、修复轮次、总耗时和工具成本。发布阻断项是**错误完成、静默覆盖用户改动、未授权写入、恢复后跳过必需验收**；其他指标与当前版本及同模型基线对照，不预设未经实测的宣传数字。
