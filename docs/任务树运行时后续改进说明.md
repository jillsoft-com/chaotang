# 任务树运行时后续改进说明

> 供开发人员实施。基于 `docs/USER-GUIDE.md`、当前 `src/services/agent/` 与 `src/services/scheduler/` 实现，以及任务树与心跳建议整理。本文件是后续工作清单，不表示所列能力已经完成。

## 1. 目标与现状

朝堂已经具备任务树调度、自主执行、执行监护、后台定时任务、工具及插件系统。任务树的 `TaskScheduler` 已采用**状态变化触发协调 + 定时巡检兜底**；后台任务由另一个 `BackgroundScheduler` 管理。后续工作应强化现有运行时的可靠性、权限和可观测性，再打通两套调度系统的唤醒与恢复契约。

不另起一套每隔数秒全量扫描所有任务的“全局心跳”。应用关闭时不承诺继续执行；重启后须先恢复状态，再按节点的副作用和授权情况决定能否续办。

| 当前实现 | 位置 | 后续关注点 |
| --- | --- | --- |
| 树级事件驱动与定时巡检 | `src/services/agent/task-scheduler.ts` | 幂等、漏唤醒、状态收束、重启恢复、巡检成本 |
| 节点执行监护 | `src/services/agent/execution-guardian.ts` | 实际工具结果、预算归因、暂停与通知 |
| 延时、周期及后续任务 | `src/services/scheduler/background-tasks.ts` | 与任务树的关联及恢复契约 |
| 朝议历史和任务树快照 | `src/stores/debate.ts` | `localStorage` 容量、全量序列化、迁移 |
| 插件 handler | `src/services/plugins/skill-parser.ts` | 动态代码隔离与能力授权 |

## 2. 实施顺序

按 **可靠性基线 → 存储与权限边界 → 并发与可观测性 → 扩展能力** 四批推进。每批须有可重复的验收场景，不能以 `vue-tsc` 和构建成功代替运行验收。完成前一批的关键验收，再开启依赖它的下一批。

### 第一批：可靠性基线

#### R1. 补齐任务树状态与恢复测试（P0）

**改动**

- 为纯数据层和调度器建立自动测试，使用可控时钟与模拟 Worker／工具，不依赖真实模型。
- 固定“树终态由所有相关叶子终态推导”的规则；父节点在子节点终结后更新，依赖失败须传播至被阻塞节点及其祖先。
- 对状态迁移结果进行检查；非法迁移不得静默忽略。树结构无效或执行异常时，等待完成的调用方必须收到失败结果，不能无限挂起。
- 恢复时区分只读、可重入操作与可能产生副作用的写操作；写操作结果未知时等待用户确认或先核查结果，不自动重复执行。
- 节点状态变化、依赖解除、工具返回、用户批准应触发协调；定时巡检负责兜底。协调须保持单棵树内互斥与事件处理幂等。

**验收场景**

1. 全成功、全失败、成功与失败混合、失败导致依赖阻塞、`partial` 与未终结节点并存，均得到正确状态；未终结节点不得提前关闭树。
2. 同一唤醒事件重复到达，不会重复执行写节点或重复发送完成通知。
3. 应用在节点执行中退出：重启后显示中断状态；用户批准续办后继续，未知结果的写操作不自行重放。
4. 树结构校验失败、节点超时及预算耗尽时，调用方得到明确状态和原因。

#### R2. 明确任务树与后台任务的唤醒契约（P1）

**改动**

- 保留 `TaskScheduler` 与 `BackgroundScheduler` 的职责边界。定义共用的唤醒记录：`sourceId`、目标树／节点、触发条件、截止时间、去重键、授权级别与处理结果。
- 后台任务若要唤醒任务树，只投递事件；实际依赖检查、状态迁移与执行仍由树调度器负责。
- 使用事件触发作为主要路径；现有定时巡检保留为兜底。只有测得唤醒延迟有问题时才调整间隔，不固定要求 2 秒全量扫描。
- 状态变化时持久化关键快照；周期性核对用于修复漏事件，不把每次 tick 全量写盘作为默认策略。

**验收场景**：时间、文件及后台任务事件各能唤醒目标节点；重复、过期和无目标事件不会产生重复执行；应用关闭期间不声称任务仍在运行。

### 第二批：存储与权限边界

#### R3. 迁移大体量数据存储（P0）

**改动**

- 引入存储接口，覆盖任务树快照、朝议历史和事件日志；业务代码不直接依赖 `localStorage` 的大对象读写。
- 桌面版优先把大对象存入应用数据目录，采用版本化格式与原子写入；浏览器版使用 IndexedDB。`localStorage` 仅保留轻量配置与索引。
- 对既有 `debates_history` 和任务树快照提供一次性迁移、失败回滚与旧数据备份。历史朝议按页／按需读取，不在启动时加载所有完整记录。
- 将事件日志与节点快照分开保存，节点只存摘要和引用，不重复嵌入完整工具输出。设定保留与清理策略。

**验收场景**：旧版本数据迁移后可打开；中途断电或写入失败不会留下半份快照；大量历史记录下仍可启动、检索和恢复；存储满额时向用户报告并保留最近的有效快照。

#### R4. 隔离插件与收紧外部工具权限（P0）

**改动**

- 插件 handler 现由 `new Function` 编译，关键字过滤不构成安全隔离。把不可信 handler 移至受限执行环境，通过有限的消息接口获得批准的能力；隔离完成前，对第三方动态 handler 加功能开关或显式信任流程。
- 为插件和 MCP Server 记录来源、请求的权限和用户授予结果；默认不给文件写入、命令执行或任意网络访问能力。
- 外部网页、文档、MCP 返回值与插件输出作为数据处理，不直接提升为系统指令。工具调用前仍须按能力与工作目录边界校验。
- 沿用现有命令安全检查，并核查路径规范化、工作目录、超时及操作审批。通用 Agent 不采用一份固定命令白名单来代替能力控制。

**验收场景**：恶意插件不能调用未授权的文件、命令或网络能力；MCP 工具越权请求被拒绝并记录；工具返回的提示注入文本不能改变系统权限；合法插件仍能在授予的能力内运行。

### 第三批：并发与可观测性

#### R5. 让只读并发声明与实际工具权限一致（P1）

**改动**

- 节点 `readOnly` 与 `allowedToolNames` 应参与实际工具注册和调用授权；不得仅凭节点标记选择并发分支，而仍把该角色全部工具交给 Worker。
- 为文件／目录资源建立读写冲突判断。写任务运行期间，对读取同一资源的节点排队或读取明确的已提交快照；不相关资源仍可并行。
- 保留写任务串行，记录等待原因与锁持有者；取消或异常时释放资源占用。

**验收场景**：只读节点无法调用写工具；读写同一文件不并发；不同资源的只读节点可并行；异常退出不遗留锁。

#### R6. 执行中展示预算与成本（P1）

**改动**

- 在每次可靠用量更新后，展示树与分支的工具调用数、迭代数、耗时及剩余预算。模型提供实际 Token 用量时采用实数；没有可靠用量时标明估算，不能将估算值作为硬停机依据。
- 预算阈值由调度器和监护器共享一套规则；警告、暂停及用户加额记录原因和操作者。通知去重，避免每次巡检重复弹窗。

**验收场景**：执行中可见分支消耗；达到上限即暂停后续执行；恢复或加额后数值连续且可追溯。

#### R7. 实现可引用的逐层汇总（P1）

**改动**

- 每个父节点在子节点都到达终态后，形成结果摘要、缺口、冲突及来源引用；摘要生成失败不应伪装成子任务完成。
- 根节点只接收下一级摘要及按需取回的证据，避免一次性注入全部叶子全文。模型意见与工具／测试证据分别标记。

**验收场景**：三层任务可逐层汇总；失败分支在根摘要中保留缺口；引用能回到对应工具结果或文件记录。

### 第四批：扩展能力

#### R8. 按模型容量管理上下文（P2）

- 现有 50,000 字符阈值可保留为未知模型的保守回退。已知模型使用 Token 估算或服务商用量，并为输出与工具结果留余量；在阈值附近压缩旧消息，保留系统约束、任务目标、最近轮次与证据引用。
- 不把“上下文窗口的 70%”写死为通用常数；按模型与任务测量压缩次数、丢失信息和实际成本。

**验收场景**：不同窗口模型不会因固定字符阈值过早压缩或超窗；压缩后仍能追溯关键证据。

#### R9. GEPA 学习成果导出与导入（P2）

- 为学习模式和事件提供版本化导出／导入、去重与冲突处理。纯本地阶段无需引入服务端；跨设备同步须另立产品需求与数据保护方案。

**验收场景**：新设备或新安装导入后可恢复学习成果；重复导入不造成重复计数。

#### R10. 用真实任务评估树深度（P3）

- 先收集三层不足的实际案例、节点数与成本数据，再决定是否开放到五层。若增加深度，仍受总节点数、单父子节点数与预算限制。
- “超深任务委托子会话”作为独立设计议题，先定义授权、上下文和结果回传协议，不在本轮默认启用。

## 3. 暂不实施的建议

- **不立即把 13 种节点状态压成 7 种。** `paused`、`interrupted`、`partial`、`blocked` 等承载不同恢复和验收语义。先补状态测试；若后续重构，须提供旧快照迁移与完整状态映射。
- **不新建覆盖所有模块的全局扫描循环。** 现有树调度器已有巡检，后台任务已有定时器；优先共享事件与恢复契约。
- **不因轮次停止自动增加预算，也不自动重放未知结果的写操作。** 预算和副作用仍由用户授权及证据决定。
- **不把 Web Worker 当作完整安全沙箱。** 插件隔离还需要明确可调用能力、IPC 边界及资源限制。

## 4. 交付要求

每个工作项交付代码、迁移说明（如涉及持久化）、对应自动测试及一段用户可理解的变化说明。验收报告须列出通过的场景和未覆盖的风险。优先完成 R1、R3、R4，再安排依赖它们的并发与体验改进；不要把构建成功当作运行时验收。
