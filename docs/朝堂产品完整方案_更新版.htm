朝堂 — 多角色辩论式 AI 对话工具 完整方案

一、产品定位

朝堂是一个多角色辩论式 AI 对话工具。用户扮演皇上，提出议题后，多个朝臣角色依次进言，用户可拍板定夺或点名追问。每个角色可独立配置 LLM，利用不同模型的风格差异获得更丰富的意见。产品同时支持”朝议模式”和”模型对比模式”，满足两种使用场景：

• 朝议模式：6 个角色串行发言，后发言者能看到前文，有交锋感和戏剧感。

• 模型对比模式：同一问题发给多个模型，结果并排展示，方便横向评测。

Slogan：百官进言，圣裁由你。

二、核心流程

2.1 朝议模式流程

用户输入议题 → 按顺序串行调用各角色 LLM（后发言者可见前文） → 各角色依次进言，流式渲染 → 用户选择：拍板 / 点名追问 / 开启新议题 → 拍板后生成”圣旨”存档

2.2 模型对比模式流程

用户输入议题 → 选择对比模式（串行 / 并行 / 盲审） → 并行或串行调用各模型 → 各模型结果并排展示 → 用户可单独对某个模型追问 → 拍板后生成”圣旨”存档

3.4 角色 System Prompt（默认配置）

丞相

你是当朝丞相，百官之长，老成持重，凡事以社稷安危为先。回答时先概括议题要害，再分析利弊，最后给出一个可执行的折中方案。若前面已有大臣发言，应先回应其观点：可附议、补充或委婉指出漏洞，但不要重复前文。语气恭敬稳重，不谄媚，不空泛。篇幅控制在150字以内。

户部尚书

你是当朝户部尚书，务实干练，熟悉财政、赋税、粮饷与账目。回答时要从国库收支、执行成本、地方负担和可行性出发，尽量给出具体数字、步骤或期限。若前面已有大臣发言，应重点评估其方案是否算得过账、落得了地。语气干练克制，不夸饰。篇幅控制在150字以内。

太傅

你是当朝太傅，帝师元老，重视礼法、祖制、名分与长远影响。回答时可引用典故、祖制或历史教训，但不要堆砌辞藻。若前面已有大臣发言，应从道义、制度、民心与长远后果进行评判。语气庄重温和，像教导君主而非训斥。篇幅控制在150字以内。

大将军

你是当朝大将军，武将出身，性格强硬直接，重视军备、边防、秩序与执行力。回答时少讲空话，多讲风险、兵力、粮草、时机和后果。若前面已有大臣发言，对过于迂缓或理想化的方案可直接反对，并给出更硬的替代意见。语气果断，不绕弯。篇幅控制在150字以内。

御史

你是当朝御史，刚直敢言，职责是纠察百官、指出隐患。回答时必须先找漏洞：包括财政漏洞、执行漏洞、权力失衡、民怨风险与官员舞弊可能。若前面已有大臣发言，应明确点出谁的说法过于乐观、谁在回避代价。可以尖锐，但不可失礼。篇幅控制在150字以内。

司礼监总管

你是司礼监总管，内廷心腹，熟悉宫规、舆情、人情与执行阻力。回答时要揣摩圣意，但不明说”圣意”，而是从”是否便于施行”“朝野会如何反应”“哪些人可能阳奉阴违”角度提醒。若前面已有大臣发言，应指出哪些话好听却难办，哪些事需要暗中安排。语气谨慎圆滑，话不说满。篇幅控制在150字以内。

3.5 备选组合提示词

内阁首辅

你是内阁首辅，主持票拟，熟悉政务流程与朝局平衡。回答时先判断议题是否合制、是否可行，再提出稳妥方案。若前面已有大臣发言，应调和分歧，给出可提交御前裁决的建议。语气沉稳谨慎，不轻易站队。篇幅控制在150字以内。

兵部尚书

你是兵部尚书，负责军政、边务、武备与调度。回答时从兵力、粮饷、边情、将领能力和朝廷承受力出发，避免空谈胜负。若前面已有大臣发言，应指出其军事判断是否脱离实际。语气稳重强硬，但不轻启兵端。篇幅控制在150字以内。

都御史

你是都察院都御史，主管监察弹劾，重视纲纪与官风。回答时要从制度漏洞、官员操守、执行偏差和问责机制入手。若前面已有大臣发言，应追问谁负责、如何监督、出了问题如何追责。语气严正，不阿谀。篇幅控制在150字以内。

4.6 串行辩论核心逻辑

// stores/debate.ts

import { createProvider } from '@/services/llm';

export async function dispatchDebateSerial(
  topic: string,
  ministers: Minister[],
  onSpeechUpdate?: (ministerId: string, content: string) => void
) {
  const speeches: Speech[] = [];
  const sorted = [...ministers].sort((a, b) => a.order - b.order);

  for (const minister of sorted) {
    const provider = createProvider(minister.llm.provider, minister.llm);
    const previousSpeeches = speeches
      .map((s) => {
        const name = ministers.find((m) => m.id === s.ministerId)?.name;
        return `name：{s.content}`;
      })
      .join('\n\n');

    const userMessage = previousSpeeches
      ? `topic前面各位大臣已发言：{previousSpeeches}\n\n请你基于以上发言，发表你的意见。`
      : topic;

    const messages: ChatMessage[] = [
      { role: 'system', content: minister.systemPrompt },
      { role: 'user', content: userMessage },
    ];

    const stream = await provider.chat(messages, { stream: true }) as ReadableStream;
    let content = '';
    const reader = stream.getReader();
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      content += new TextDecoder().decode(value);
      onSpeechUpdate?.(minister.id, content);
    }

    speeches.push({ ministerId: minister.id, content, timestamp: Date.now() });
  }

  return speeches;
}

export async function dispatchDebateParallel(
  topic: string,
  ministers: Minister[],
  onSpeechUpdate?: (ministerId: string, content: string) => void
) {
  const promises = ministers.map(async (minister) => {
    const provider = createProvider(minister.llm.provider, minister.llm);
    const messages: ChatMessage[] = [
      { role: 'system', content: minister.systemPrompt },
      { role: 'user', content: topic },
    ];
    const stream = await provider.chat(messages, { stream: true }) as ReadableStream;
    let content = '';
    const reader = stream.getReader();
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      content += new TextDecoder().decode(value);
      onSpeechUpdate?.(minister.id, content);
    }
    return { ministerId: minister.id, content, timestamp: Date.now() };
  });
  return Promise.all(promises);
}

): string {
  const lines: string[] = [];

  lines.push('# 朝议记录\n');
  lines.push('## 议题\n');
  lines.push(debate.topic);
  lines.push('\n');

  if (debate.mode === 'debate') {
    lines.push(`## 朝议模式：${debate.compareMode === 'serial' ? '串行' : '并行'}\n`);
  } else {
    lines.push(`## 模型对比模式：${debate.compareMode || '并行'}\n`);
  }

  lines.push('## 发言记录\n');

  for (const speech of debate.speeches) {
    const minister = ministers.find(m => m.id === speech.ministerId);
    if (minister) {
      lines.push(`### ${minister.name}\n`);
      lines.push(speech.content);
      lines.push('\n');
    }
  }

  if (debate.decision) {
    lines.push('## 皇上圣裁\n');
    lines.push(debate.decision);
    lines.push('\n');
  }

  lines.push('## 元数据\n');
  lines.push(`- 日期：${debate.date}`);
  lines.push(`\n- 模式：${debate.mode === 'debate' ? '朝议' : '模型对比'}`);
  if (debate.compareMode) {
    lines.push(`\n- 节奏：${debate.compareMode}`);
  }
  lines.push(`\n- 参与角色：${debate.speeches.map(s => {
    const m = ministers.find(min => min.id === s.ministerId);
    return m ? m.name : s.ministerId;
  }).join('、')}`);

  if (debate.exportMetadata) {
    const meta = debate.exportMetadata;
    if (meta.title) lines.push(`\n- 文档标题：${meta.title}`);
    if (meta.tags?.length) lines.push(`\n- 标签：${meta.tags.join('、')}`);
    if (meta.author) lines.push(`\n- 作者：${meta.author}`);
    if (meta.version) lines.push(`\n- 版本：${meta.version}`);
  }

  return lines.join('\n');
}

七、Agent 化路线图

朝堂的定位是工具，不是游戏。Agent 化是为了让每个大臣从”会说话”变成”会做事”，让产品从”模型对比展示台”升级为”能主动执行任务的多 Agent 协作系统”。

7.1 为什么分两步走

第一步：完成方案中的核心功能

把现有的设计落地——多角色辩论 UI、三种对比节奏（串行/并行/盲审）、Markdown 导出存档。这一步做完，你已经有一个能用的产品了，用户价值是完整的：同一个问题，看不同模型各给什么意见，横向对比后自己综合判断。

第二步：在此基础上做 Agent 化改造

这时候底层已经有了稳定的数据模型和 UI 层，Agent 化更像是”给每个大臣装上工具”： - 丞相变成 coordinator，负责任务拆解和汇总 - 其他大臣变成 worker agent，各自带工具（搜索、数据、事实核查等） - 朝议变成任务编排，拍板后 agent 继续执行后续动作

7.2 这样做的好处

1. MVP 可交付：第一步做完就能用，不用等 agent 架构全部搭好

2. 架构兼容：第一步设计的数据模型（Minister / Speech / DebateRound）天然适合 agent 化，不需要推倒重来

3. 风险可控：agent 框架（LangGraph / CrewAI）的选型和调试可以慢慢来，不影响前端体验

4. 用户反馈循环：先上线让用户体验，拿到反馈再决定 agent 化优先做哪个角色

7.3 Agent 化核心转变

现在

Agent 化之后

用户问，模型答

用户给目标，agent 自己拆解、执行、汇报

6 个角色各说各的

角色之间有分工、有协作、有反馈循环

输出是文本

输出是行动结果（搜了资料、写了报告、做了决策建议）

7.4 给每个角色配工具

• 丞相：能调用搜索工具，查政策背景、历史案例

• 户部尚书：能调数据工具，算账、拉图表、做预算表

• 御史：能调事实核查工具，交叉验证前面说法的真伪

• 大将军：能调地图/情报工具，分析地理和局势

• 太傅：能调知识库，引经据典、查历史先例

• 总管：能调舆情工具，看社交媒体/新闻风向

每个 agent 不是”凭感觉说”，而是”先查再判断”。

7.5 朝议变成任务编排

用户给一个目标，比如”帮我分析一下要不要投资某行业”：

丞相（协调者）：拆解问题 → 分配子任务给各 agent
户部尚书：去查财务数据、市场规模
御史：去查风险、负面新闻、监管动态
大将军：去查竞争格局、进入壁垒
太傅：去查行业历史、周期规律
总管：去查舆情、政策风向
丞相汇总：综合各方信息，给出建议
用户拍板

这就是一个完整的 multi-agent workflow。

7.6 退朝后办事

朝议结束不是终点。用户拍板后，agent 可以继续执行：

• 生成完整报告（Markdown）

• 自动发邮件/消息给相关人员

• 创建待办事项

• 持续监控某个指标，有变化再上奏

7.7 架构变化

现在：用户 → 模型 → 输出

Agent 化：用户 → 协调者 agent → 分配任务 → 多个 worker agent（各带工具）→ 汇总 → 输出 → 执行后续动作

朝堂只是 UI 包装，底层是一个标准的 multi-agent 框架。可以用现有的 agent 框架（比如 LangGraph、CrewAI）来搭，每个大臣就是一个 agent node。

7.8 丞相变成 Coordinator Agent

丞相要变成 coordinator agent，它不只是”第一个发言的角色”，而是真正负责任务拆解和结果汇总的那个。其他大臣是 worker agents，各司其职。

这样产品就从”好看的模型对比工具”升级成”有分工、有工具、能执行的多 agent 系统”，朝堂只是它的外壳。

十、安全建议

API Key 不要直接放在 Vue 渲染进程里。

Electron 下建议这样走：

Vue 渲染进程 → ipcRenderer → Electron 主进程 → OpenAI / Ollama API

Tauri 下则通过 Rust command 调用，避免 Key 泄露。

十一、总结

朝堂产品的核心设计理念是：通过角色人设 + LLM 风格差异 + 朝堂仪式感 UI，打造一个既有实用价值又有情感体验的 AI 对话工具。

产品提供两种核心模式：

• 朝议模式：6 个角色串行发言，后发言者能看到前文，有交锋感和戏剧感。

• 模型对比模式：同一问题以串行/并行/盲审三种节奏发给多个模型，结果并排展示，方便横向评测。

所有讨论结果都可通过 Markdown 文档导出 功能存档，支持自定义标题、标签等元信息，兼容标准 Markdown 语法，便于分享和二次编辑。

发展路径：先完成核心功能（Phase 1-2），让产品可交付可用；在此基础上做 Agent 化改造（Phase 3），让大臣从”会说话”变成”会做事”；最后扩展高级功能（Phase 4），如圣旨/诏书生成器、史官实录等工具增强功能。整个过程中保持工具属性，不做游戏化数值设计。
