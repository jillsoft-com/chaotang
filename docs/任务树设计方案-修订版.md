# 朝堂任务树与执行监护设计方案（修订版）

> 供讨论的设计稿，2026-10-11。依据现有 [任务树 + 心跳监护设计方案](./任务树设计方案.md)、补充的任务树／心跳建议及当前 Agent 模式代码拟定；尚未实现。

## 一、结论与取舍

原案要解决的问题准确：丞相一次拆出扁平任务后，Worker 不能再组织自己的工作，跨任务依赖也难表达。建议保留“丞相总规划、Worker 按需细化、叶子任务执行、结果逐层汇聚”这一主线。主结构是树，横向依赖另成无环图；调度采用**事件驱动、低频定时兜底**。规则负责进度、预算与停滞判断，模型只给建议，完成与授权由可核查的证据和用户决定。

| 原案设想 | 本稿调整 | 理由 |
| --- | --- | --- |
| 先建完整树，再执行所有叶子 | 丞相给一级计划；某节点依赖满足、即将执行时，才由该 Worker 判断是否细化 | 后续任务可读到前序真实结果，避免过早拆解及多次无用模型调用 |
| 节点同时保存 `children` 与 `nodeMap` | 只保存 `nodes: Record<id, node>`、`parentId` 和有序 `childIds` | 避免两份节点数据不一致，也便于 JSON 持久化 |
| `decomposed`、`sleeping` 等与运行状态混用 | 结构、执行状态、等待原因分别保存；父节点状态按子节点推导 | 更容易解释“已拆解但被依赖阻塞”等情况 |
| 心跳模型可终止、恢复、调高轮次 | 规则引擎可暂停和报警；模型只能建议；预算增加与越权恢复须经用户批准 | 防止模型误判“已完成”或自行扩大执行权限 |
| 第三期才持久化任务树 | 第一版就保存轻量快照；重启后转为“已中断”，人工确认后续办 | 没有状态记录便无法可靠展示进度或恢复 |
| 默认仅同父节点依赖 | 允许跨分支依赖，但必须校验无环、无祖先或后代引用 | 开发流水线中的“测试等待前后端完成”往往跨分支 |
| 心跳只在工具轮次后运行 | 状态变化立即调度，低频定时巡检超时及等待条件 | 工具未返回、时间条件已到时也需发现问题；无任务时无需空转 |
| 结果只传给丞相 | 每个父节点产生摘要、冲突与缺口，再递归上送 | 大树不应把所有叶子的全文一次塞给根节点 |

本案**不承诺应用关闭后仍执行任务**。第一版只在应用运行时推进；关闭或崩溃后的任务展示为“已中断”，不会自动重复写文件或跑命令。所谓“自动恢复”只适用于已获授权、结果可核查且重复执行安全的步骤，不能作为所有工具的默认行为。

补充建议中的“分层任务网络（HTN）+ LLM”和“controller loop”可作为设计思路，但不是产品能力证明。LangGraph、CrewAI、AutoGen 的概念不能逐列等同；朝堂是否具备企业可用的审计与恢复能力，要看实际状态记录、权限边界和故障演练结果。递归拆解亦不必然比少量清晰任务更好，须以交付质量和成本实测。

**暂不吸收的做法：**固定每 2 秒全量扫树、每个 tick 调模型、轮次上限后自动加额、失败节点一律自动重试，以及把并发写文件作为第一版目标。这些做法会提高成本或重复副作用；只有已登记的等待条件和可重入的只读操作适合自动唤醒。

## 二、与现有实现的衔接

当前 `CoordinatorAgent` 的 `runAgentDebate()` 是“丞相拆解 → 用户批准 → 逐个 Worker 执行 → 丞相汇总”；`WorkerTask` 已有 `autonomous` 字段。`AutonomousEngine` 最多迭代 10 轮，但 `[GOAL_REACHED]` 由模型自行输出，逐轮验证主要是一段提醒。计划批准在 `ChatSession.vue`，文件写入仍由 Electron 主进程另行批准。

新方案只替换 **Phase 2 的调度方式**。Phase 1 的模型、角色绑定、计划确认及 Phase 3 的丞相汇总继续复用。旧版扁平 `TaskDecomposition.tasks` 可映射为根节点的一级子节点；打开历史会话时无需重新跑任务。

## 三、用户可见的目标

输入“做一个价格计算页面并验证”后，用户应能看到：

```text
议题：价格计算页面
├─ 前端实现〔进行中〕
│  ├─ 建立表单组件〔已完成；文件已确认〕
│  └─ 接入价格函数〔进行中；等候写入批准〕
├─ 价格规则〔已完成；测试 4/4 通过〕
└─ 验收测试〔等待前端实现、价格规则〕
```

点开节点能看任务目标、负责人、依赖、验收条件、工具证据、最近错误和所耗轮次。用户可暂停整棵树、终止节点、批准计划变化或要求重试。界面须区分“模型说已完成”和“按验收条件已核实”。

## 四、数据模型

运行态不直接混入长期保存的会话文本。下列为可序列化快照的核心字段；完整工具输出留在现有调用记录，节点只保存摘要或引用。

```ts
type TaskStatus =
  | 'pending' | 'ready' | 'running' | 'awaiting_approval'
  | 'waiting' | 'paused' | 'interrupted' | 'completed' | 'partial' | 'failed'
  | 'blocked' | 'skipped' | 'cancelled'

type Verification = 'none' | 'model_claim' | 'tool_evidence' | 'user_confirmed'
type TaskDependency = { taskId: string; kind: 'required' | 'advisory' }
type WakeCondition =
  | { type: 'time'; notBefore: number }
  | { type: 'external_event'; source: string; key: string }

interface TaskBudget {
  maxIterations: number
  maxToolCalls: number
  timeoutMs: number
  maxInputTokens?: number          // 仅在服务商提供可靠用量时做硬门槛
}

interface TaskUsage {
  iterations: number
  toolCalls: number
  inputTokens?: number             // 实测值；估算值另标 estimated
  outputTokens?: number
  elapsedMs: number
}

interface TaskNode {
  id: string                       // UUID，不用层级编号当身份
  parentId: string | null
  childIds: string[]                // 顺序用于展示，不代表依赖
  title: string
  description: string
  createdBy: string                // 角色 ID 或 user
  assigneeId: string | null         // 仅限本次已选角色；根节点为空
  requiredForParent: boolean       // 必需子任务失败时，父节点不可正常完成
  mode: 'analysis' | 'action'
  autonomous: boolean
  decomposition: 'unexamined' | 'leaf' | 'expanded'
  dependencies: TaskDependency[]    // 可指向其他分支的父节点
  priority: 0 | 1 | 2 | 3          // 同时就绪时排序；3 最高
  readOnly: boolean
  allowedToolNames: string[]        // 本角色已有工具的子集，不扩权
  requiresApproval: boolean
  acceptance: string[]              // 可检查的交付物或人工判断标准
  status: TaskStatus
  waitingReason?: string            // 如“等待 A 完成”“等待用户批准写入”
  wakeCondition?: WakeCondition     // 仅 waiting 状态可有；第一版只支持时间
  verification: Verification
  resultSummary?: string
  unresolvedQuestions: string[]
  inputRefs: string[]               // 引用 ID，用时按需取原文
  evidenceRefs: string[]            // 工具调用 ID、文件路径、测试记录 ID
  budget: TaskBudget
  usage: TaskUsage
  maxRetries: number
  attempt: number
  revision: number
  createdAt: number
  startedAt?: number
  finishedAt?: number
}

interface TaskTreeSnapshot {
  schemaVersion: 1
  runId: string
  debateId: string
  rootId: string
  nodes: Record<string, TaskNode>
  planRevision: number
  usage: TaskUsage                 // 全树汇总；节点用量归因见各节点
  state: 'planning' | 'awaiting_approval' | 'running'
       | 'paused' | 'interrupted' | 'completed' | 'completed_with_gaps'
       | 'failed' | 'cancelled'
  limits: {
    maxDepth: number                // 默认 3：根为 0，可有一级至三级任务
    maxChildren: number             // 默认 5
    maxNodes: number                // 默认 20，含根节点
    maxIterationsPerLeaf: number    // 默认沿用现有 10
    maxToolCallsPerRun: number      // 全树总预算
    maxEstimatedTokensPerRun?: number // 估算软上限；触顶先停止新调用并请示
  }
  updatedAt: number
}
```

**结构与状态约束：**

1. 有子节点的是汇聚节点，不直接调用工具；无子节点的叶子节点才执行。父节点 `completed` 仅在全部必需子节点完成且父级验收条件满足时成立。用户接受缺口时可置为 `partial`，根任务显示 `completed_with_gaps`，不可与完整成功混同。
2. `childIds`、`parentId` 和 `dependencies` 必须引用存在的节点；不许自依赖、依赖自己的祖先或后代、也不许出现任何环。跨分支依赖支持“验收测试等待整个前端分支完成”。`required` 未完成会阻塞，`advisory` 可使用已有摘要先行，但界面须标明证据可能过期。
3. `pending` 表示尚未具备条件；`ready` 表示必需依赖已满足；`waiting` 表示等待明确的时间或外部事件；`blocked` 表示必需依赖失败或验收不能继续；`skipped` 表示用户明确跳过；`paused` 是用户或监护规则主动暂停；`awaiting_approval` 不得自动恢复。
4. `verification` 与 `status` 分开：分析任务可完成而验证等级为 `model_claim`；需要构建或测试的行动任务，不能仅凭 `[GOAL_REACHED]` 达到 `tool_evidence`。
5. `rootId` 属于整棵树，节点的深度和展示路径可从父链推导，不重复存储。角色 ID、深度、子节点数、任务总数、依赖环及工具权限必须在接收模型 JSON 后由代码校验。无效计划不得直接执行；可重试一次解析，仍失败则沿用旧版扁平计划并提示用户。
6. `createdBy`、状态变迁、用量和来源引用保留审计记录。原始命令、工具参数及模型上下文可能含密钥，默认只保存脱敏摘要；需要完整记录时由用户明确开启并限定保留期。

## 五、规划与调度

### 5.1 初始计划和渐进拆解

丞相先生成一级任务、负责人、交付物、关键依赖及 `autonomous` 建议，并展示给用户批准。计划不要求预先填满所有子节点。调度器遇到一个 `ready`、尚未分析过的节点时，调用该角色模型一次，让它选择“直接执行”或“拆成 2～5 个可验收子任务”。达到最大深度、任务上限或模型输出不合规时，该节点按叶子执行或交用户决定；不得悄悄丢弃任务。

Worker 拆解输出必须包含每个子任务的**交付物、验收条件、所需工具类别和依赖**。提示模型“多文件”并不必然要拆；只有独立验收或有先后关系的工作才值得成为子节点。拆解后先做质量检查：子任务合并后是否覆盖父目标、是否明显重叠、是否有不可执行的空泛任务、验收标准能否逐项判断。校验不通过时允许 Worker 修订一次，再交丞相兜底或请用户定夺。

用户能预览树变更；超出原批准范围、换角色、增加写入或命令权限、提高预算的变化必须再次批准。子任务仍受既有文件写入及命令审批约束。可执行粒度的判断是“可由现有工具或一次明确分析完成，并可验收”，不以子任务数量越多越好。

### 5.2 就绪判定与顺序

```text
循环：
  校验整棵树的结构和依赖
  找出必需依赖均已完成、未暂停、未取消的 ready 节点
  按优先级、计划顺序、节点 ID 稳定排序，取第一个
  原子地占用该节点（第一版同一时刻只执行一个节点）
  若可拆且未分析：按需分析并提交树变更
  若为叶子：用现有标准执行器或 AutonomousEngine 执行
  收集工具证据并按验收条件核对
  更新节点及父节点状态，保存快照，再选择下一个
  无 ready 节点时：区分全部完成、等待时间／事件、等待批准、依赖失败、死锁
```

第一版保持**单节点串行执行**，因多个 Worker 共用同一工作目录；并行写文件容易互相覆盖。同一角色也只执行一个任务。日后可先放开只读节点并行，再为写操作增加文件锁与冲突处理。依赖决定可执行性，优先级只决定多个就绪节点谁先执行；优先级不能越过必需依赖。后续节点只接收**父目标、已完成依赖的摘要、引用 ID、全局约束及未解决问题**，避免把整棵树与失败尝试都塞进模型上下文。超出上下文预算时要注明“引用内容未取全”，不可静默截断后仍声称已全面核查。

### 5.3 失败与汇总

叶子失败后，只阻塞真正**强依赖**它的节点；无关节点继续。弱依赖节点可先行，但必须记录所用数据的版本和缺口。用户可重试失败节点，重试会新增 `attempt`，保留旧证据并重新校验下游。父节点若有任一必需子节点失败，应显示“失败／部分完成”，不能写成“已完成”；皇上明确接受缺口后才可转为 `partial`，此状态不满足下游强依赖。

**逐层汇总**由该父节点的负责人完成：先合并子节点结论与产出，再列出互相矛盾的事实或判断、证据出处、未回答的问题和本层建议。父摘要保存引用 ID，全文按需加载。只有一个子节点且结果明确时可机械汇总，避免额外模型费用。丞相最终汇总只读取各一级节点的结构化摘要；须分别列出完成、失败、阻塞、跳过与未验证项，并保留无法裁决的分歧。用户可选择接受“有缺口的结果”，系统不得替他把缺口改写成成功。

**核查任务**可由御史或指定角色执行，但作为被核查任务的后续兄弟节点，或作为该节点的验收阶段，不能把核查任务挂在被核查节点下又依赖父节点完成。核查应指出证据等级、反证和引用来源；通过后提升 `verification`，不通过则退回修订或呈交皇上。模型不能只凭另一模型的赞同就提升为 `tool_evidence`。

## 六、执行监护：事件触发 + 定时兜底

任务树是期望与实际状态，调度器负责**协调跨角色任务**；单个 Worker 的 ReAct／自主执行循环仍由 `AutonomousEngine` 负责。心跳不是每隔几秒就请模型“看看要不要做事”，而是一个确定性的协调循环：

```text
状态事件或定时 tick
  → 读取快照及版本号
  → 校验依赖、等待条件、超时、预算和正在运行的任务
  → 生成状态迁移候选
  → 以版本号检查后提交迁移，保存事件
  → 将就绪任务交给执行队列；通知父节点或用户
```

应用级只有**一个调度服务**，每棵任务树保留独立状态；第一版执行队列并发上限为 1。丞相计划批准、工具返回、依赖完成、用户暂停／继续等事件立即触发一次协调。定时巡检只兜底发现模型请求超时、时间等待到期和漏掉的状态变化：活跃任务可每 10 秒检查，只有等待条件时可每 30 秒检查，无活动树则停表。间隔是可调上限，不是承诺精确到秒；**应用关闭后没有 tick**。第一版调度逻辑放在独立服务模块，不绑在聊天组件的渲染定时器上；因现有模型与工具在渲染进程，跨进程迁移须另设 IPC 协议，不能只把计时器搬到主进程便声称可靠。

调度器只做协调：`pending → ready`、`waiting → ready`、检查超时、通知父节点汇总、记录统计。它不能替仍在运行的 Worker 擅自把任务标为成功。每次状态迁移校验 `revision` 和当前 `runId`，同一节点同一版本只允许一个调度动作；工具调用另用幂等键与执行记录识别重复。崩溃后“已发出但未收到结果”的写入、命令或消息属于**结果未知**，先核查产物，不自动重发。

第一版仅自动唤醒两类条件：**必需依赖完成**、**明确的本机时间到达**。等待文件变化或 Webhook 可列入后续版本，但必须有受信任事件来源、订阅记录和去重键；不能让模型随意写一段条件文字供心跳执行。等皇上批准的节点始终保持 `awaiting_approval`，不能靠定时 tick 越权唤醒。轮次或总预算触顶时暂停并请求皇上裁决；即使全树尚有预算，单节点上限也不能自动提高。

规则指标包括：总轮次、全树工具调用数、失败次数、距上次有效进展的时间、重复调用指纹、已执行验收项。连续 3 次相同工具与规范化参数，或连续 3 次相同错误且产物未变化，判为疑似循环；读取分页或轮询等预期重复应有例外。触发后先暂停该节点，展示证据和建议，允许用户修改指令后重试。**自动重试只适用于声明为只读、可重入的临时失败**，且有最大次数与退避时间；写入、Git、命令、Webhook 等默认由用户确认重试。

可选的轻量模型只回答“可能原因和下一步建议”，不能直接把任务设为完成、绕过审批、取消依赖或增加预算。任何调整上限均需用户批准，并受应用硬上限约束。`[GOAL_REACHED]` 只是一条模型声明；需结合文件存在、工具返回、测试结果或用户确认，才可更新验证等级。按角色、节点、分支汇总 Token、耗时和工具次数；服务商未返回用量时标记为估算值，不能冒充精确账单。

现有 `AutonomousEngine` 需要在每轮开始前及每次工具执行前检查暂停／取消信号。新接口可接收 `AbortSignal` 和 `onCheckpoint`；若当前模型服务不支持中断正在进行的请求，界面须说明“将在本次请求结束后停止”，不可承诺立即终止。调度器记录每次巡检的扫描节点数、状态迁移数、耗时与错误，但不因空 tick 大量写盘。通知用事件 ID 去重并设冷却时间；第一版只做应用内通知，桌面或外部消息待真正接好再扩展。

**关键状态迁移：**

| 从 | 到 | 触发与前提 |
| --- | --- | --- |
| `pending` | `ready` | 必需依赖完成，且运行未暂停 |
| `pending`／`ready` | `waiting` | 已登记可验证的唤醒条件 |
| `ready` | `running` | 调度器取得节点执行权，并确认预算和批准仍有效 |
| `running` | `completed` | 产物已形成，验收条件逐项检查并记录验证等级 |
| `failed`／`blocked` | `partial` | 仅汇聚节点可用；用户明确接受已列出的缺口 |
| `running` | `failed`／`paused` | 确认失败，或达到循环／预算保护条件 |
| `waiting` | `ready` | 时间或已订阅事件到达，且运行仍获授权 |
| `failed` | `ready` | 限定的只读临时失败自动重试，或用户明确批准重试 |
| `running` | `interrupted` | 应用重启后发现结果未知，等待核查 |

任何通向 `cancelled` 的操作须由用户或明确的上层取消事件触发；`awaiting_approval` 只有用户批准才可继续。无法形成上述合法迁移时，协调器记录原因，不得默默改状态。

## 七、状态保存与恢复

第一版把**小型任务树快照**关联到 `Debate`，每次计划批准、节点状态变化、工具完成后保存；限制节点摘要长度，不在 `localStorage` 重复存储长输出、密钥或完整文件内容。保存失败时暂停并提示用户，不能继续执行却显示“已保存”。事件记录包含 `runId`、递增 `seq`、`nodeId`、时间、前后状态与证据引用，便于定位问题；对模型上下文和日志中的密钥做遮盖。

启动时把遗留的 `running` 节点标为 `interrupted`，展示上次工具结果与“执行结果未知”提示，由用户选择“重新核对后继续”或“终止”。原本 `awaiting_approval` 的节点保持待批准，并重新展示计划或命令内容；绝不沿用未完成的弹窗。整棵树先处于中断态，用户恢复后才处理已到期的等待条件。**不自动重放最后一次工具调用**，尤其不重放写入、Git、Webhook 与命令。后续版本可把事件日志和快照迁至 Electron 应用数据目录，采用原子写入；网页模式只提供查看与手动重试。

## 八、界面与事件

计划批准框应显示可滚动的任务树，而不只是一句“是否批准执行”。会话右侧任务面板展示一级节点和可折叠子节点；节点上显示状态、负责人、优先级、依赖及“已验证／待验证”标记。节点详情展示目标、验收条件、用量与预算、最近 3 条执行事件、工具证据、引用来源和失败原因。原有 Worker 发言仍保留，树只负责进度与证据，不复制每轮长文本。父节点展开后应能看出本层摘要、冲突和未解决问题，而不只见子节点清单。

事件可新增 `tree-created`、`node-expanded`、`node-ready`、`node-started`、`node-checkpoint`、`node-paused`、`node-completed`、`node-failed`、`tree-updated`，统一携带 `runId`、`nodeId` 和 `seq`。在 `ChatSession.vue` 用事件更新任务树状态，并保留旧 `worker-start/worker-done` 兼容原会话显示。用户可“暂停全部”“终止节点”“重试节点”“查看证据”；操作按钮须显示会影响哪些依赖任务。

## 九、实现顺序与验收

### 第一期：可信任务树（优先）

1. 新增纯数据模块 `task-tree.ts`：结构校验、强弱依赖判定、拓扑就绪判定、状态迁移、父节点汇聚、快照序列化。先写确定性的单元测试。
2. 在 `coordinator.ts` 中把现有 `WorkerTask[]` 映射成一级树，沿用 Plan Mode、角色模型绑定与工具审批；先不让 Worker 再拆，以核实迁移无回归。
3. 加入按需拆解和节点数、深度、全局调用预算；模型 JSON 必须经过校验。界面先用朴素树列表，提供计划变更确认。
4. 新增独立 `task-scheduler.ts`：状态事件立即协调，低频 tick 只巡检超时、等待时间与漏掉的状态变化；第一版串行执行。
5. 每次关键状态变化保存快照；重启后标记中断，不自动续跑。旧历史没有任务树时继续按旧格式展示。

**验收：**无环依赖、强弱依赖、跨分支依赖、优先级排序、失败隔离、用户拒绝计划、工作目录写入审批、重启后中断标记均有测试；连续触发两次相同事件只调度一次；用 `tests/acceptance` 的折扣样本实跑，模型声称完成但 `npm test` 失败时，节点不得显示“已验证”。

### 第二期：执行监护

1. 增加 `execution-guardian.ts`，先实现纯规则循环检测、停滞检测、全局预算与通知去重。
2. 给 `AutonomousEngine` 增加检查点、暂停／取消协作及证据报告；可选模型建议放在规则稳定后。
3. 加入节点详情中的监护记录、节点与分支成本归因及重试操作，不允许监护器自行提高上限。

**验收：**三次同参失败触发暂停；不同参数的正常重试不误判；只读临时失败在次数限制内退避重试，写入失败不自动重放；用户拒绝后不会再次执行工具；取消时不启动下一次工具；全树预算耗尽时所有未开始节点保持未完成；重复通知只展示一次。

### 第三期：体验与扩展

加入只读任务并行、手动调整依赖、可信的文件变化／Webhook 唤醒源、事件日志导出与更可靠的桌面持久化。跨角色委派须重新核对所选角色和权限；应用关闭后定时执行属于另一个后台任务设计，暂不纳入本案。

## 十、建议先决定的产品问题

1. 用户是否需要**编辑丞相计划**，还是只批准／退回？本稿先支持批准、退回和重试，编辑可在下一版加入。
2. 某个分析任务没有可执行检查时，是否允许“模型输出即完成”？本稿允许完成，但必须标记为 `model_claim`，不显示为已验证。
3. 任务树默认是否面向所有朝议？建议第一版只在 Agent 模式启用；串行和并行议事继续保持轻量。
4. 要不要在第一版开放弱依赖给模型自行声明？建议先由丞相提出、用户可在计划批准时查看；弱依赖的旧证据必须显著标记。
