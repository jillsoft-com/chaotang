
# 任务树 + 心跳监护 设计方案

## 1. 问题分析

**当前架构（扁平结构）：**
```
丞相拆解 → [Task A, Task B, Task C] → 逐个执行 → 丞相汇总
```

局限：
- 丞相一次性拆解，Worker 只是被动执行，缺乏自主分析能力
- 复杂任务无法进一步细化（如"前端开发"内部还有"组件/路由/状态管理"等子任务）
- 所有任务都在同一层级，无法表达依赖关系和执行优先级

**目标架构（任务树）：**
```
丞相拆解 → 一级任务树
  ├── Task A（前端开发）
  │   ├── Sub-A1: 创建组件
  │   ├── Sub-A2: 实现路由
  │   └── Sub-A3: 状态管理
  ├── Task B（后端开发）
  │   ├── Sub-B1: 数据模型
  │   └── Sub-B2: API 接口
  └── Task C（测试）
      ├── Sub-C1: 单元测试
      └── Sub-C2: 集成测试
```

## 2. 核心数据模型

新增文件：`src/services/agent/task-tree.ts`

```typescript
/** 任务节点 — 任务树的基本单元 */
export interface TaskNode {
  id: string                    // 唯一标识（如 "task-1", "task-1-2"）
  title: string                 // 简短标题（如 "创建组件"）
  description: string           // 详细描述（包含交付物要求）
  assigneeId: string            // 执行者角色 ID
  level: number                 // 层级（0 = 根任务/议题, 1 = 丞相拆解, 2+ = Worker 拆解）
  parentId?: string             // 父任务 ID
  children: TaskNode[]          // 子任务列表
  status: TaskStatus            // 执行状态
  autonomous: boolean           // 是否启用自主执行
  dependsOn?: string[]          // 依赖的兄弟任务 ID（同一父节点下）
  result?: TaskResult           // 执行结果
  context?: string              // 补充上下文
  createdAt: number
  startedAt?: number
  completedAt?: number
}

export type TaskStatus =
  | 'pending'       // 等待执行
  | 'analyzing'     // 正在分析（Worker 决定是否拆解）
  | 'decomposed'    // 已拆解为子任务
  | 'executing'     // 正在执行（叶子节点）
  | 'paused'        // 已暂停（心跳监护者暂停，等待依赖/用户确认）
  | 'sleeping'      // 休眠（等待唤起条件满足）
  | 'completed'     // 完成
  | 'failed'        // 失败
  | 'skipped'       // 跳过（依赖失败）
  | 'terminated'    // 被心跳监护者终止

export interface TaskResult {
  content: string               // 执行输出内容
  toolCalls: ToolCallResult[]   // 工具调用记录
  duration: number              // 耗时(ms)
  summary?: string              // 结果摘要（用于传递给兄弟/父节点）
}

/** 完整任务树 */
export interface TaskTree {
  root: TaskNode                // 根节点（代表整个议题）
  maxDepth: number              // 最大深度限制（默认 3）
  nodeMap: Map<string, TaskNode> // 快速索引
}
```

## 3. 执行流程

### 3.1 三阶段流程

```
阶段 1: 构建树
  用户议题
    → 丞相拆解为 Level 1 任务（分配给各 Worker）
      → 每个 Worker 分析自己的任务
        → 决定是否拆解为 Level 2 子任务
          → Level 2 子任务可进一步拆解为 Level 3（受 maxDepth 限制）

阶段 2: 执行叶子节点
  遍历任务树，找到所有叶子节点
    → 按依赖关系排序（dependsOn）
    → 依次执行（使用 AutonomousEngine 或标准模式）
    → 执行结果写入 TaskNode.result

阶段 3: 结果汇聚
  从叶子向根逐层汇聚：
    → 父节点收集所有子节点的 result.summary
    → 丞相做最终汇总
```

### 3.2 Worker 分析与拆解协议

当 Worker 接收到一级任务后，系统注入"任务分析"提示词：

```
你收到了一项任务。请先分析是否需要拆解：

**需要拆解的情况：**
- 任务包含多个独立的步骤或阶段
- 任务涉及不同类型的产出物（如多个文件、多个模块）
- 某些步骤之间有明确的先后依赖关系

**不需要拆解的情况：**
- 任务本身就是单一的、原子性的操作
- 任务只需一次性分析和建议

如果需要拆解，输出 JSON：
{
  "needDecompose": true,
  "analysis": "你对任务的分析",
  "subtasks": [
    {
      "title": "子任务标题",
      "description": "详细描述和交付物要求",
      "autonomous": true/false,
      "dependsOn": []
    }
  ]
}

如果不需要拆解：
{
  "needDecompose": false,
  "analysis": "你对任务的分析",
  "executionPlan": "你的执行计划"
}
```

### 3.3 执行规则

| 规则 | 说明 |
|------|------|
| 叶子优先 | 只有叶子节点才会被实际执行 |
| 依赖排序 | 同一父节点下的子任务按 `dependsOn` 拓扑排序 |
| 结果传递 | 子任务完成后，其 `result.summary` 传递给后续兄弟任务和父节点 |
| 失败隔离 | 某子任务失败时，仅跳过依赖它的兄弟任务，不影响无关任务 |
| 深度限制 | 最大 3 层（含丞相拆解层），超过则强制作为叶子执行 |
| 子任务上限 | 每个节点最多拆解为 5 个子任务 |

## 4. 心跳监护系统（Heartbeat Guardian）

### 4.1 问题：被动超时 vs 主动监护

**当前模式（被动）：**
```
任务启动 → 盲目执行 → 到达轮次上限 → 强制停止
```
问题：
- 任务已完成但还没到上限，浪费 Token
- 任务陷入死循环，只等上限才能停
- 无法根据实际进展动态调整策略
- 没有"暂停后恢复"的能力

**心跳模式（主动）：**
```
任务启动 → 心跳监护者定期评估 → 智能决策
                                ├── CONTINUE  — 进展正常，继续执行
                                ├── PAUSE     — 暂停等待（依赖/用户确认）
                                ├── TERMINATE — 终止（已完成或不可恢复）
                                ├── RESUME    — 唤起之前暂停的任务
                                ├── NOTIFY    — 通知用户介入
                                └── ADJUST    — 调整参数（增减迭代上限等）
```

### 4.2 设计定位

心跳监护者是**独立的系统组件**，不依赖任何角色的 LLM：

- 使用轻量级模型（如 `summary_model_id` 配置的摘要模型）做评估，节省成本
- 与丞相解耦：丞相负责任务拆解，心跳负责执行期监控
- 可配置评估间隔（默认每 3 轮工具调用评估一次）

### 4.3 核心类型

新增文件：`src/services/agent/heartbeat-guardian.ts`

```typescript
/** 心跳监护者配置 */
export interface HeartbeatConfig {
  /** 评估间隔：每 N 轮工具调用后触发一次心跳评估（默认 3） */
  intervalRounds: number
  /** 心跳评估使用的 LLM（默认用摘要模型，轻量省钱） */
  modelId?: string
  /** 是否启用通知（当需要用户介入时） */
  notifyEnabled: boolean
  /** 单任务最大心跳次数（防止无限监控） */
  maxHeartbeats: number
}

/** 心跳评估决策 */
export type HeartbeatDecision =
  | 'continue'    // 继续执行
  | 'pause'       // 暂停（等待依赖/用户确认）
  | 'terminate'   // 终止（目标已达成 / 不可恢复）
  | 'resume'      // 唤起之前暂停的任务
  | 'notify'      // 通知用户介入
  | 'adjust'      // 调整执行参数

/** 心跳评估结果 */
export interface HeartbeatReport {
  taskId: string
  decision: HeartbeatDecision
  reason: string            // 决策理由
  metrics: TaskMetrics      // 任务健康指标
  suggestion?: string       // 给用户/执行器的建议
}

/** 任务健康指标 */
export interface TaskMetrics {
  iterations: number        // 已执行轮数
  successRate: number       // 工具调用成功率
  lastProgressAt: number    // 最后一次有效进展的时间
  tokenEstimate: number     // 预估 Token 消耗
  isLooping: boolean        // 是否检测到循环（重复调用相同工具+参数）
  goalProximity: number     // 目标接近度（0-1，由 LLM 评估）
}
```

### 4.4 心跳评估协议

心跳监护者每次评估时，向 LLM 发送以下信息：

```
你是一个任务健康监护者。请评估以下任务的执行状态并做出决策。

## 任务信息
- 任务：{task.description}
- 执行者：{assignee.name}
- 已执行轮数：{metrics.iterations}
- 工具调用成功率：{metrics.successRate}
- 距上次有效进展：{timeSinceLastProgress}
- 是否检测到循环：{metrics.isLooping}

## 最近 3 轮的执行记录
{recentToolCallSummaries}

## 最近输出摘要
{recentContentSummary}

## 请评估并输出 JSON
{
  "decision": "continue|pause|terminate|resume|notify|adjust",
  "reason": "你的评估理由",
  "goalProximity": 0.0-1.0,
  "suggestion": "具体建议（可选）"
}
```

### 4.5 心跳与任务树的协作

```
心跳监护者定期扫描任务树：

任务树
├── Task A (executing) ← 心跳评估：进展正常 → CONTINUE
│   ├── Sub-A1 (completed)
│   └── Sub-A2 (executing) ← 心跳评估：循环检测 → PAUSE + NOTIFY
├── Task B (paused) ← 心跳评估：依赖已解除 → RESUME
│   └── Sub-B1 (pending)
└── Task C (executing) ← 心跳评估：目标达成 → TERMINATE
    └── Sub-C1 (completed)
```

### 4.6 循环检测算法

心跳监护者内置规则引擎（不依赖 LLM）做循环检测：

```typescript
function detectLoop(toolCalls: ToolCallResult[]): boolean {
  // 检查最近 N 次工具调用是否存在重复模式
  // 规则：连续 3 次调用相同工具 + 相同参数 = 循环
  // 规则：连续 3 次 execute_command 返回相同错误 = 循环
}
```

### 4.7 通知机制

当心跳决策为 `notify` 时，系统通过以下方式通知用户：

1. **UI 通知**：在任务树展示区弹出提示卡片
2. **会话消息**：在 ChatSession 中插入一条"心跳监护者"的系统消息
3. **用户选项**：提供操作按钮（继续执行 / 终止任务 / 修改指令后重试）

## 5. 整体架构

```
                    ┌─────────────┐
                    │ Coordinator │  ← 编排整体流程
                    │  Agent      │
                    └──────┬──────┘
                           │
                    ┌──────┴──────┐
                    │  TaskTree   │  ← 管理树结构、遍历、依赖解析
                    │  Executor   │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
        ┌─────▼─────┐ ┌───▼───┐ ┌─────▼─────┐
        │ Worker A  │ │Worker │ │ Worker C  │
        │ (拆解+执行)│ │  B    │ │ (拆解+执行)│
        └─────┬─────┘ └───┬───┘ └─────┬─────┘
              │            │            │
        ┌─────▼─────┐ ┌───▼───┐ ┌─────▼─────┐
        │Autonomous │ │标准执行│ │Autonomous │
        │  Engine   │ │ 循环  │ │  Engine   │
        └─────┬─────┘ └───┬───┘ └─────┬─────┘
              │            │            │
              └────────────┼────────────┘
                           │
                    ┌──────▼──────┐
                    │ Heartbeat   │  ← 独立监护者，定期评估所有活跃任务
                    │  Guardian   │    循环检测(规则引擎) + 状态评估(轻量LLM)
                    └─────────────┘
```

### 文件职责划分

| 文件 | 职责 |
|------|------|
| `coordinator.ts` | Phase 1 丞相拆解 + Phase 3 丞相汇总 + 整体编排 |
| `task-tree.ts`（新增） | TaskTree 类：构建树、Worker 拆解、遍历执行、结果汇聚 |
| `heartbeat-guardian.ts`（新增） | 心跳监护者：定期评估任务健康、做决策、循环检测、通知 |
| `autonomous-engine.ts` | 单叶子节点的自主执行（接受心跳监护者的决策指令） |

### 修改点

**`coordinator.ts`：**
- `WorkerTask` 类型不变（兼容现有逻辑）
- `TaskDecomposition` 扩展为 `TaskTree` 的 Level 1
- Phase 2 的 Worker 循环逻辑移交给 `TaskTreeExecutor`
- `formatDecomposition()` 改为树形展示

**`task-tree.ts`（新增）：**
- `TaskTree` 类：管理树结构（增删改查节点、遍历）
- `TaskTreeExecutor` 类：执行任务树（分析→拆解→执行→汇聚）
- `analyzeTask()` 方法：LLM 分析是否需要拆解
- `executeTaskTree()` 方法：按拓扑序执行叶子节点
- `aggregateResults()` 方法：从叶子向根汇聚结果

**`heartbeat-guardian.ts`（新增）：**
- `HeartbeatGuardian` 类：独立监护者
- `evaluate()` 方法：评估单个任务的健康状态
- `evaluateAll()` 方法：批量评估所有活跃任务
- `detectLoop()` 方法：规则引擎检测循环
- `applyDecision()` 方法：执行心跳决策（暂停/终止/唤起/通知）

**`autonomous-engine.ts`：**
- `execute()` 方法接受可选的 `heartbeatCallback`，每 N 轮调用一次
- 新增 `pause()`/`resume()`/`terminate()` 方法供心跳监护者调用
- 不再依赖 `maxIterations` 作为唯一终止条件，心跳可提前终止或延长

## 8. 实现策略

分三期实现：

### 第一期（任务树核心）

1. 创建 `task-tree.ts`，实现 `TaskNode`/`TaskTree` 数据模型
2. 实现 `TaskTreeExecutor`：Worker 分析→拆解→执行→汇聚
3. 修改 `coordinator.ts`：Phase 2 委托给 `TaskTreeExecutor`
4. 更新丞相拆解的 JSON 格式（支持 `subtasks` 字段）
5. 更新 `formatDecomposition` 为树形展示
6. 新增事件类型
7. 更新 USER-GUIDE.md

### 第二期（心跳监护）

1. 创建 `heartbeat-guardian.ts`，实现 HeartbeatGuardian
2. 实现循环检测规则引擎（纯逻辑，不依赖 LLM）
3. 实现心跳评估协议（轻量 LLM 评估）
4. 集成到 AutonomousEngine：`heartbeatCallback` 回调机制
5. 实现通知机制（UI 卡片 + 用户操作按钮）
6. 新增心跳相关事件类型

### 第三期（增强，后续）

1. UI 树形可视化组件（可折叠/展开）
2. 子任务级别的进度展示
3. 跨角色子任务分配（Worker 可将子任务委托给其他角色）
4. 任务树持久化（保存到 debate 记录，支持回放）
5. 心跳历史面板（查看每次评估的决策和理由）
6. 任务依赖图可视化
